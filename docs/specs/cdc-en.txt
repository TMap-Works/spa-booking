1. Introduction and context
1.1 Purpose of this document
This document is the scoping dossier for the design and delivery of a booking application for spas and beauty salons, whose MVP (Minimum Viable Product) functional scope was defined in the “Spa & Salon Booking App — MVP Feature Scope” document. It has three objectives:
Translate the MVP functional scope into a concrete, sequenced and estimated implementation plan (roadmap, phases, sprints, milestones);
Define the target technical architecture and the selected technology stack;
Specify in detail the infrastructure requirements on Amazon Web Services (AWS), including services, sizing, security, compliance and a budget estimate.
It serves as a shared reference across product leadership, the development team, the infrastructure/DevOps team and the project sponsors.
1.2 Product vision
The application aims to give beauty institutes, spas, hair salons, barbershops and massage studios an all-in-one management platform: online booking for clients, an administration dashboard for the back office, team and availability management, in-store checkout, automated notifications and activity reporting. The reference platform, Booker (Mindbody group), illustrates the market standard.

2. Target technical architecture
2.1 Architecture principles
The retained architecture favors simplicity of delivery at the MVP stage while preserving the ability to evolve toward a multi-location, multi-tenant platform. The guiding principles are:
Modular monolith first. A single application backend, structured into decoupled business modules (booking, catalog, staff, payments, notifications, reporting), rather than a premature microservices architecture. This lowers the operational cost of the MVP while allowing later extraction into separate services.
Cloud-native and managed. Systematic use of managed AWS services (databases, queues, notifications) to minimize the operational burden.
Multi-tenant by design. Logical data isolation per establishment (tenant_id) from the data model onward, to prepare for onboarding several salons without a rewrite.
API-first. A versioned REST/JSON API exposes all capabilities, consumed by the client web app, the admin dashboard and a future mobile app.
Security and compliance by default. Encryption at rest and in transit, outsourcing of PCI-DSS compliance to the payment provider, adherence to GDPR principles on client data.

3. Implementation roadmap and plan
1-month target — delivery model
This plan compresses the full MVP scope into 4 weeks. It is an aggressive timeline that is achievable only under specific conditions (see assumptions below): an experienced cross-functional team working fully in parallel, reliance on managed AWS services and proven starter templates, third-party providers for payments and messaging (no in-house build), and a strictly frozen scope.
3.1 Methodology
The project runs in Agile mode with one-week sprints. Work is split across parallel workstreams (infrastructure/DevOps, backend, frontend, QA) so that domains progress simultaneously rather than sequentially. Each week ends with a demonstrable increment.
Sprint length: 1 week.
Total MVP duration: 4 weeks (1 month), i.e. 4 sprints.
Ceremonies: weekly planning, daily stand-up, weekly review and retrospective; demo at the end of each week.
Definition of Done (DoD): code reviewed, tested (unit + integration), deployed to the staging environment, documented.

4. AWS infrastructure requirements
4.1 Guiding infrastructure principles
The infrastructure design follows the AWS Well-Architected Framework and its six pillars: operational excellence, security, reliability, performance efficiency, cost optimization and sustainability. The structuring choices are:
Serverless containers. The application runs on Amazon ECS with Fargate: no servers to administer, automatic scaling.
Multi-AZ high availability. Spread across at least two Availability Zones for production (compute and database).
Everything as Infrastructure-as-Code. The whole stack is described in Terraform/CDK, versioned and deployed reproducibly to each environment.
Least privilege. Granular IAM roles, isolated secrets, network segmented into public/private subnets.
Primary region. Selection of an AWS region suited to user location and data-residency requirements (e.g. eu-west-1/eu-west-3 for Europe/Africa); global CDN via CloudFront.
4.2 Target architecture overview
The logical flow below runs from the user to the data services. Inbound traffic is protected by the CDN and the web application firewall, distributed by a load balancer to the application containers, which rely on a managed relational database, a cache, object storage and notification services.

4.9 Payments and PCI-DSS compliance
Payment processing is delegated to a PCI-DSS Level 1 certified provider (Stripe or equivalent). The application never stores card numbers: it handles only tokens. This approach greatly reduces the PCI compliance scope on our side (SAQ A self-assessment).
Client-side tokenization. Card data flows directly from the browser to the provider; our backend only ever receives a token.
Secure webhooks. Payment events (success, failure, refund) are received via signed, verified webhooks.
Logging and reconciliation. Transaction history kept on the application side, reconciled against provider statements.
No card data at rest. Stronger compliance posture, minimal audit scope.

5. Security, compliance and data protection
Beyond the infrastructure measures (section 4.10), protecting client personal data is a cross-cutting requirement. The application processes personal data (identity, contact details, appointment history, notes) subject to applicable regulations (GDPR in Europe and equivalent frameworks).
5.1 Data protection principles
Minimization. Collect only the data strictly necessary for booking and client follow-up.
Consent and purposes. Clear user information, explicit legal basis for each processing activity (notifications, later marketing).
Data-subject rights. Mechanisms for access, rectification, export and deletion of data (right to be forgotten).
Encryption. Systematic encryption at rest (KMS) and in transit (TLS).
Multi-tenant isolation. Strict logical isolation of data between establishments.
Data residency. AWS region choice consistent with localization obligations.
5.2 Payment compliance
Delegating card processing to a PCI-DSS Level 1 provider and storing no card data reduces the compliance scope on our side to a simplified self-assessment (SAQ A). Webhooks and API keys are secured via Secrets Manager.
